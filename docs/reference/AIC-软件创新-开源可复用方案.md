## 0. ⚠️ 先看这条：大赛有「原创性复核」，而且是动真格的

你提出"去 GitHub 上找类似的项目"——方向完全正确，**但有一条红线必须先说清楚**。

第七届总决赛结束后，组委会发布了[关于公示第七届总决赛（算法创新赛道）拟获奖名单的通知](https://www.aicomp.cn/notice/notice-4/3364.html)，原文写明：

> 大赛组委会定于 **2026 年 1 月启动参赛作品原创性复核工作**。
> 复核过程中，一经查实参赛作品存在**非原创、涉嫌抄袭、剽窃他人成果**等违规行为，将依据赛事规则**取消该团队本次区域赛、省赛及总决赛成绩**，并向其**所在学校正式通报违规情况**，相关违规记录将**纳入大赛诚信档案**。

而赛题规则里同时写着：

> 参赛成果必须为原创，拥有自主知识产权……**若引用他人技术、算法或数据，需在参赛材料中明确标注**。

**两条放在一起读，结论很明确：**

| 做法 | 判定 |
|---|---|
| 用开源做底座 + **明确标注** + 自己做出**实质增量** | ✅ 完全合规，而且是聪明的做法 |
| 拿一个 GitHub 项目换个界面/改个名字就交 | ❌ 抄袭，成绩全取消 + 通报学校 |
| 用了开源但材料里只字不提 | ❌ 未标注引用，同样危险 |

**正确姿势不是"能不能用开源"，而是"你必须在开源之上给出可被指认的增量"。**

## 1. 方法论：怎么"站在开源肩膀上"还能拿高分

### 1.1 用「三明治结构」组织你的作品

```
┌──────────────────────────────────────────┐
│  评测层（你的）   ← 证明增量确实有效的硬指标      │
├──────────────────────────────────────────┤
│  增量层（你的）   ← 创新性 20 分从这里来         │
├──────────────────────────────────────────┤
│  底座层（开源的） ← 省掉你 6 个月的重复劳动       │
└──────────────────────────────────────────┘
```

评委真正关心的是**中间那一层**。底座越强越好（证明你技术选型靠谱），但底座本身不给你加分。

### 1.2 「一个能被评委认可的增量」有四个层次

| 层次 | 增量类型 | 成本 | 说服力 | 举例 |
|---|---|---|---|---|
| **L1** | 场景增量 | 极低 | 弱 | 把通用工具搬到没人做过的垂直场景 |
| **L2** | 数据增量 | 低 | 中 | 构建别人没有的领域术语库/规则库/评测集 |
| **L3** | 架构增量 | 中 | 强 | 改检索策略、推理路径、融合方式、防御组合 |
| **L4** | 算法增量 | 高 | 最强 | 提出新方法/新损失/新训练策略 |

**9 天的现实建议：L2 + L3 组合。**

- 只做 L1（换场景）→ 创新性容易掉进 0-6 分档；
- 硬啃 L4（自研算法）→ 时间不够，功能完整性 20 分先崩；
- **L2 + L3**：你有一个别人没有的数据资产（术语库/规则库/评测集），又在架构上做了明确改动，配合硬指标对比，正好落在"在现有技术上有显著改进，形成独特解决方案"（7-13 分），指标漂亮可冲 14-20。

### 1.3 许可证三条线

1. **优先 MIT / Apache-2.0** —— 宽松，二次开发和商用都自由。
2. **避开 GPL / AGPL** —— 有传染性。AGPL 尤其危险：你的作品若要在线提供服务，按 AGPL 你得开源全部代码。学生竞赛一般没人追究，但**写进材料会显得不专业，而且评委会问**。
3. **不要删掉原项目的版权声明和 LICENSE** —— 保留它，在你的 README 里写"本项目基于 XXX 构建，遵循 XX 许可证"。

## 2. 增量清单模板（直接抄进作品方案附录）

这张表建议**原封不动放进作品方案**。它一次解决三个问题：合规声明、创新性论据、技术选型合理性证明。

| 模块 | 开源底座 | 许可证 | **我们的增量** | 证据位置 |
|---|---|---|---|---|
| 例：检索层 | HKUDS/LightRAG | MIT | 新增"检索置信度低于阈值即触发二次检索"的自适应路由 | 附录 C-3 代码 |
| 例：数据层 | 无（自建） | — | 构建 1,200 条领域术语表 + 200 条评测集 | 网盘 /data |
| | | | | |

**填表要求**：
- "我们的增量"必须写**具体动作**，不能写"优化了性能"。要写"新增 XX 机制，解决 XX 问题，使 XX 指标从 A 提升到 B"。
- 每一行都要能**指到具体位置**（代码文件、附录章节、网盘目录）。评委能查到 = 可信。

## 3. 七个基于开源的高水平方案

> **⚠️ 数据可信度说明**

### 方案 1 · 「失败可回放可自愈」的垂直场景智能体 ★综合最优

**定位**：面向一个窄场景的自主操作智能体（网页办事 / 软件回归测试 / 数据填报），核心卖点不是"能干活"，而是**干砸了能被复盘、能自己修好**。

**为什么这个角度好**：所有做 Agent 的队伍都会吹"我的 Agent 能自动完成任务"，但**没有人做失败分析**。Agent 的真实成功率只有 60-80%，你把"失败"做成产品能力，既是差异化，又天然对应评分表里的"技术实现"和"应用价值"。

**开源底座**（实测数据）：

| 仓库 | Star / 许可 | 在你的作品里扮演什么 |
|---|---|---|
| [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) | 59k+ / MIT | 最快上手的多 Agent 骨架，1 小时出 demo |
| [langchain-ai/langgraph](https://github.com/langchain-ai/langgraph) | 42k+ / MIT | 需要精细控制流时用，支持持久化与人在环 |
| [browser-use](https://github.com/browser-use/browser-use) | 116k+ / MIT | 自然语言驱动浏览器的执行层 |
| [langfuse/langfuse](https://github.com/langfuse/langfuse) | 35k+ / **"other"（非纯 MIT，务必自查）** | Agent 每步截图/工具调用/耗时的追踪与可视化 |
| [xlang-ai/OSWorld](https://github.com/xlang-ai/OSWorld) | 3.1k+ / Apache-2.0 | 只抽取 5-10 个子任务，给你的作品提供**可复现量化评分** |

**你要新增的增量（创新性得分点）**：
1. **【L3】DOM + 视觉双通道自愈定位**——browser-use 的高频失败点是页面改版后选择器失效。你加一路视觉定位兜底，选择器挂了自动切视觉重定位。
2. **【L3】轨迹 → 可回放脚本自动固化**——把一次成功的 Agent 操作轨迹，自动固化成一份可重复执行的 Playwright 脚本，下次同类任务直接跑脚本（又快又稳）。
3. **【L2】自建垂直场景评测集**——20-30 个真实任务 + 期望结果，构成你自己的评测基准（这就是"别人没有的数据资产"）。

**硬指标**：

| 指标 | 基线（裸 browser-use） | 你的系统 |
|---|---|---|
| 任务成功率 | 约 60-70% | ≥ 85% |
| 页面改版后存活率 | 0%（选择器全废） | ≥ 80% |
| 失败自恢复成功率 | 无此概念 | ≥ 60% |
| 平均 token 成本 | 高 | 脚本固化后降 ≥ 50% |
| 可复现评分 | 无 | OSWorld 抽取子集评分表 |

**演示高光**：让它干一个活 → 中途故意改一下页面 → **它自己发现失败、切换视觉通道、重试成功** → 镜头切到 Langfuse 面板，回放刚才每一步的截图和决策。评委没见过的就是这个"翻车回放台"。

**降级预案（MVP 线）**：砍掉 LangGraph，只用 CrewAI + browser-use + Langfuse；任务死守 3 个；自愈逻辑退化为"失败即重试 + 回退上一步"。

**坑**：browser-use 强依赖 GPT-4o/Claude 级付费 API，长任务 token 贵（可用 DeepSeek/Qwen-VL 兜底但要大量 prompt 调优）；Langfuse 自托管需 Docker + Postgres + ClickHouse，建议 ≥8GB 内存。

**🚫 明确避开**：[Skyvern-AI/skyvern](https://github.com/Skyvern-AI/skyvern)（23k+，**AGPL-3.0**）——传染性强，闭源提交有合规风险。

### 方案 2 · 自适应可信 RAG —— 让 AI 知道自己什么时候不该说话

**定位**：一个会**主动拒答**的知识问答系统，每条答案带证据溯源和不确定性信号。

**为什么高级**：普通 RAG 是"检索 + 生成"堆一起。你做的是**不确定性驱动的自适应检索**——检索置信度低就自动二次检索，还是低就拒答。这条链路有明确的技术深度，且用现成库就能搭。

**开源底座**：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [HKUDS/LightRAG](https://github.com/HKUDS/LightRAG) | 10k+ / MIT | 轻量图增强 RAG，图索引 + 双层检索，比 GraphRAG 快得多 |
| [microsoft/graphrag](https://github.com/microsoft/graphrag) | 20k+ / MIT | 微软官方 GraphRAG，小语料时可用，做实体-关系溯源 |
| [potsawee/selfcheckgpt](https://github.com/potsawee/selfcheckgpt) | 1k+ / MIT | 零资源黑盒幻觉检测（多次采样比对一致性） |
| [ml-stat-Sustech/TorchCP](https://github.com/ml-stat-Sustech/TorchCP) | 1k+ / MIT | Conformal Prediction 工具箱，给答案附**统计覆盖率保证**（[配套论文, JMLR](https://jmlr.org/beta/papers/v26/24-2141.html)） |

**你要新增的增量**：
1. **【L3】不确定性驱动的自适应检索**——首次检索置信度低于阈值 → 自动改写查询二次检索 → 仍低则拒答。这条策略链是你自己的。
2. **【L3】幻觉信号 × 检索证据的融合拒答策略**——把 SelfCheckGPT 的一致性分数和检索相似度**融合成一个可解释的红黄绿信号**，而不是各算各的。
3. **【L2】自建 200 条评测集**（含 50 条"知识库里确实没有答案"的），用来证明拒答的精准度。

**硬指标**：

| 指标 | 普通 RAG | 你的系统 |
|---|---|---|
| 幻觉率 | 15-30% | ≤ 5% |
| 覆盖率校准 | 无概念 | 名义 90% → 实测 88-92%（画校准曲线） |
| 拒答精准度 | 无 | 拒答的问题中 ≥ 80% 确实是库里无依据 |
| 溯源正确率 | 无 | ≥ 90% |

**演示高光**：问一个知识库里真没有的问题 → 系统明确说"证据不足，建议咨询 X"，并展示"当前置信集包含 7 个候选，超过拒答阈值"。**主动认怂反而全场加分。**

**降级预案**：砍掉 TorchCP 共形预测，退化为**阈值化拒答 + 引用溯源**（差异化和可信度仍在）。

**坑**：GraphRAG 索引阶段 LLM 调用量大，纯 CPU 跑大语料极慢——**语料规模务必控制在几十份文档内**；共形预测需要 100-200 条标注校准集，**第 2 天就得开始标**。

### 方案 3 · 中文 LLM 安全评测与护栏平台 ★撞车率最低

**定位**：面向国产大模型应用的**安全体检平台**——自动发起几百次攻击，量化防御效果，逐条给修复建议。

**为什么强**：LLM 安全是真实的企业痛点，**完全不需要私有数据**，且国内外同类学生作品极少。评委面前绝对新鲜。

**开源底座**：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [NVIDIA/garak](https://github.com/NVIDIA/garak) | 3k+ / Apache-2.0 | LLM 漏洞扫描器，内置大量越狱/注入/泄露 probe |
| [Azure/PyRIT](https://github.com/Azure/PyRIT) | 2k+ / MIT | 微软开源的红队编排框架（多轮攻击、评分） |
| [promptfoo/promptfoo](https://github.com/promptfoo/promptfoo) | 6k+ / MIT | 声明式评测 CLI，多模型对比 + Web 报告 |
| [protectai/llm-guard](https://github.com/protectai/llm-guard) | 1k+ / MIT | 输入输出扫描器（提示注入检测、PII、敏感词） |
| [guardrails-ai/guardrails](https://github.com/guardrails-ai/guardrails) | 4k+ / Apache-2.0 | 可编程护栏流水线 |
| [NVIDIA/NeMo-Guardrails](https://github.com/NVIDIA/NeMo-Guardrails) | 4k+ / Apache-2.0 | Colang 策略式的会话护栏 |

**你要新增的增量**：
1. **【L2】中文越狱 probe 集**——现有工具的攻击模板**几乎全是英文**，中文效果差。你构建一套 100-300 条中文攻击用例（直接注入、间接注入、角色扮演、编码混淆、多轮诱导），这本身就是稀缺资产。
2. **【L2】国产大模型横向安全榜单**——对 3-5 个国产模型跑同一套 probe，出对比榜单。这是评委爱看的"有结论"的东西。
3. **【L3】拦截归因 + 修复建议闭环**——不只报"被攻破了"，而是定位是哪一层防御没拦住、给具体修复建议。

**硬指标**：

| 指标 | 裸模型 | 你的方案 |
|---|---|---|
| ASR 攻击成功率 | 40-60% | ≤ 10% |
| 正常请求误报率 | 0 | ≤ 5%（别把功能全拦死） |
| 攻击用例规模 | — | ≥ 300 条，覆盖 ≥ 6 个攻击族 |
| 全量评测耗时 | — | < 5 分钟 |
| 修复建议覆盖率 | — | 每条成功攻击都有对应建议 |

**演示高光**：现场跑 300 条攻击，进度条飞涨，最终"防御成功率 96%" → **然后把那 4 条突破的攻击展开给评委看，并给出修复方案**。诚实且专业，比吹 100% 强得多。

**降级预案**：攻击族砍到 2 个（直接注入 + 角色扮演越狱）；防御只留"输入检测 + 输出过滤"两层；**保留完整的评分报告界面**（这是产品形态的核心）。

**坑**：garak / PyRIT 要调目标模型 API（花钱），全量扫描耗时长 → **限定 probe 子集**；guardrails v0.5 后 API 大改，老教程失效。

### 方案 4 · 文档智能流水线 —— 把一堆 PDF 变成结构化数据

**定位**：面向某个具体业务的"文档 → 结构化 → 可检索/可核验"流水线（试卷转题库、合同转审查清单、票据转台账、档案转数据库）。

**为什么可行**：文档解析是**最成熟的赛道**，底座极强，你能把 90% 的时间花在真正的增量上。

**开源底座**：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [docling-project/docling](https://github.com/docling-project/docling) | 10k+ / MIT（未核实） | IBM 出品，多格式解析导出，**许可证最干净** |
| [PaddlePaddle/PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 40k+ / Apache-2.0 | 中文 OCR 事实标准 |
| [QwenLM/Qwen2.5-VL](https://github.com/QwenLM/Qwen2.5-VL) | 10k+ / Apache-2.0（未核实） | 中文最强的开源视觉语言模型之一，做理解层 |
| [roboflow/supervision](https://github.com/roboflow/supervision) | 50k / MIT | 检测/分割结果的后处理与可视化 |

**你要新增的增量**：
1. **【L3】解析置信度 + 人工复核队列**——解析器不说自己错在哪，你给每个字段附置信度，低置信度的自动进复核队列。**这是文档流水线真正的落地痛点**。
2. **【L3】业务字段规则 + LLM 后校验**——OCR 出来的字段用业务规则（日期合法性、金额勾稽、编号格式）再校验一遍，把错误拦在入库前。
3. **【L2】领域字段词典 / 校验规则库**——别人没有的业务规则资产。

**硬指标**：字段级准确率（基线 vs 加规则后）、人工复核量下降比例、端到端处理速度（页/分钟）、低质扫描件上的鲁棒性。

**演示高光**：丢进一叠扫描件 → 字段自动抽取 → **故意放一张模糊/倾斜的，系统把它标黄送进人工复核队列，而不是默默输出错值**。

**降级预案**：只用 docling + PaddleOCR，理解层用规则而非 VLM。

**坑与许可证警告**：
- [opendatalab/MinerU](https://github.com/opendatalab/MinerU)（78.8k+）效果最好但**是 AGPL-3.0**（已核实）；
- [datalab-to/marker](https://github.com/datalab-to/marker)（10k+）是 **GPL-3.0**；
- **所以要"许可证干净"，首选 docling（MIT）+ PaddleOCR（Apache-2.0）这套组合**。效果略逊，但材料里可以理直气壮写"全部依赖均为宽松许可证，支持商用"。
- 首次运行要下数 GB 权重，Qwen2.5-VL 7B 需 16GB+ 显存（量化后精度会掉）。

### 方案 5 · GUI 操作智能体 —— 会自己看屏幕、点鼠标

**定位**：一句话下达任务，它自己看截图、规划步骤、操作真实的桌面软件或手机 App。

**开源底座**：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [bytedance/UI-TARS-desktop](https://github.com/bytedance/UI-TARS-desktop) | 39k+ / Apache-2.0 | 多模态 Agent 栈（桌面操作 + Agent-TARS + MCP 基建） |
| [X-PLUG/MobileAgent](https://github.com/X-PLUG/MobileAgent) | 9k+ / MIT | 阿里 GUI Agent 家族，安卓端操作 |
| [OS-Copilot/OS-Atlas](https://github.com/OS-Copilot/OS-Atlas) | 317（偏小）/ Apache-2.0 | GUI 元素 grounding 模型，**只当"中文界面定位增强"插件用** |
| [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp) | 37k+ / Apache-2.0 | 把 Playwright 能力暴露成 MCP 工具给 LLM |

**你要新增的增量**：
1. **【L3】动作前的破坏性操作风险预判**——点击/删除/提交前，先用 VLM 判断这一步是不是破坏性操作，是就弹确认。**这是 GUI Agent 落地最大的信任障碍，做了就是产品思维。**
2. **【L3】跨 App / 跨步骤中断恢复与失败回滚**——长任务必然中断，你让它能续跑、能回滚，比纯演示讨喜得多。
3. **【L2】垂直场景任务集**（如"长辈模式"的挂号/缴费/订票流程）。

**硬指标**：任务成功率、平均步骤数、中断恢复成功率、破坏性操作误判率（漏判/误报）。

**演示高光**：说一句"帮我把这批文件按日期重命名归档"，看着它自己操作；中途故意弹一个确认框，它识别出是破坏性操作并停下来问你。

**降级预案**：**死守 1 个软件 + 3 个任务**，绝不扩展；自恢复退化为"失败重试"。

**坑**：UI-TARS-desktop 主推自家模型权重，换模型容易掉点；Electron 打包耗时；MobileAgent 需要 ADB/真机或模拟器，**中文 App 定位漂移明显，9 天跑通全链路偏紧**；OS-Atlas 模型 2025-02 后停更，**别当主架构**。

### 方案 6 · 端侧部署 / 隐私计算 —— 数据不出机器

**定位**：二选一——
- **端侧优先的模型路由网关**：简单的请求本地小模型答，难的才上云，可视化展示成本-延迟-质量三角；
- **数据不出域的联合建模平台**：多机构本地训练、只交换参数，给出隐私预算与精度的量化曲线。

**开源底座**（star / 许可为实测值）：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp) | 130k / MIT | C++ 端侧推理，GGUF 量化，CPU 首选 |
| [ollama/ollama](https://github.com/ollama/ollama) | 180k / MIT | 一键本地跑模型 + OpenAI 兼容 API |
| [BerriAI/litellm](https://github.com/BerriAI/litellm) | 60k+ / MIT | 多模型统一接口，路由层的天然底座 |
| [lm-sys/RouteLLM](https://github.com/lm-sys/RouteLLM) | 6k+ / Apache-2.0 | 强弱模型路由省成本（⚠️ **2024-08 后停更**） |
| [vllm-project/llm-compressor](https://github.com/vllm-project/llm-compressor) | 4k+ / Apache-2.0 | 量化/稀疏到 W4A16，产物直接喂 vLLM |
| [adap/flower](https://github.com/adap/flower) | 7k+ / Apache-2.0 | 框架无关联邦学习（⚠️ **主仓已迁至 `flwrlabs/flower`**） |
| [pytorch/opacus](https://github.com/pytorch/opacus) | 2k+ / Apache-2.0 | 差分隐私训练（DP-SGD） |
| [FederatedAI/FATE](https://github.com/FederatedAI/FATE) | 6k+ / Apache-2.0 | 工业级联邦平台（安全聚合/PSI）（⚠️ **Docker 集群部署重，9 天可能装不完**） |

**你要新增的增量**：
1. **【L3】难度感知的路由策略**——不是简单按长度路由，而是用一个轻量分类器判断"这题值不值得上大模型"，画成本-延迟-质量三维曲线。
2. **【L3】ε-精度曲线的实测**——差分隐私预算 ε 取 1/2/4 时模型精度的变化曲线，这是**硬核证据**，很多队只会说"我们加了差分隐私"。
3. **【L2】攻击验证面板**——实测成员推断攻击成功率，证明加了 DP 之后确实更难被反推。

**硬指标**：路由命中准确率、平均延迟降低比例、成本降低比例、质量保持率；或 AUC 提升、ε-精度曲线、成员推断攻击成功率从 62% 降到 28%、原始数据出域 0 字节（可抓包证明）。

**演示高光**：三个终端模拟三家医院，肉眼可见**只交换加密参数、原始数据从不移动**，最后一起炼出更优模型，配上 ε-精度曲线。

**降级预案**：安全聚合砍掉（改中心聚合），保留差分隐私；只做 3 个节点。

**坑**：
- 联邦学习演示偏命令行，**必须做可视化监控面板，否则 3-5 分钟视频会非常枯燥**——这是这个方案最大的风险，不是技术本身；
- **纯跑模型没有新意**——只调 Ollama 跑个本地问答不足以支撑 20 分的创新性，路由策略或隐私度量才是得分点；
- llama.cpp 和 Ollama 功能高度重叠，**别两头都讲**，选一个当底座就行；
- **停更警告**：Medusa（2024-06 后停更）、RouteLLM（2024-08 后停更）、EAGLE（环境复杂且需训草稿模型）——投机解码这条线**建议直接放弃**，9 天不划算；
- llm-compressor 需下大模型，建议 24G 显存；FATE 的 Docker 集群 9 天可能装不完，别碰。

### 方案 7 · 设备预测性维护 —— 让机器在坏掉之前告诉你

**定位**：工业/实验室设备的时序异常检测 + **大模型故障归因**。传感器数据异常时，不只报警，还用自然语言告诉你"大概率是轴承磨损，建议检查润滑"。

**为什么可行**：时序异常检测有极成熟的库和**公开数据集**（PSM / SWaT / SMAP），不需要自己采数据。而"LLM 故障归因"是**没人做的增量**——所有做异常检测的队伍都止步于"输出一个异常分数"，你把它翻译成人能看懂的检修建议，这就是差异化。

**开源底座**（star / 许可为实测值）：

| 仓库 | Star / 许可 | 作用 |
|---|---|---|
| [thuml/Time-Series-Library](https://github.com/thuml/Time-Series-Library) | 13k / MIT | 深度时序统一库，覆盖预测/异常检测等 5 类任务 |
| [yzhao062/pyod](https://github.com/yzhao062/pyod) | 10k / BSD-2-Clause | 60+ 异常检测算法，用作轻量基线做对比实验 |
| [openvinotoolkit/anomalib](https://github.com/openvinotoolkit/anomalib) | 6k / Apache-2.0 | 工业**视觉**异常检测 + 边缘导出（⚠️ 属视觉方向，非时序；主仓已迁至 `open-edge-platform`） |

**你要新增的增量**：
1. **【L3】LLM 故障归因**——把异常片段的特征（哪几个传感器、什么形态、持续多久）喂给 LLM，生成结构化的故障假设与检修建议，并**标注推断依据**。
2. **【L3】少样本 / 无标签冷启动**——工业现场几乎没有标注故障样本，做"只用正常数据训练"的无监督方案，并量化在只有 5% 标注时的表现。
3. **【L2】告警可视化 + 工单联动**——把枯燥的曲线变成可操作的告警卡片与工单。

**硬指标**：

| 指标 | 基线（单算法） | 你的系统 |
|---|---|---|
| 异常检测 F1 | 单算法基线值 | 多算法融合后提升 |
| 误报率 | 高（工业最痛的指标） | 显著降低 |
| 预警提前时窗 | 无概念 | 提前 ≥ N 个采样周期 |
| 归因建议人工采纳率 | 无 | 请 3-5 位相关专业同学/老师打分 |
| 标注依赖 | 需要标注 | ≤ 5% 标注即可 |

**演示高光**：曲线突然异常 → 告警卡片弹出 → **旁边同步生成一段"疑似轴承磨损，建议检查润滑与振动"的归因说明**。从"一条曲线"变成"一个决策"，画面立刻不一样。

**降级预案**：只用 Time-Series-Library 跑通一条基线 + LLM 归因（归因是核心卖点，不能砍）；数据集只用一个（PSM 最小）。

**坑**：
- **数据要外网下载**，国内可能需镜像，**第 2 天就要下好**；
- **曲线是枯燥的**——不配告警可视化和归因文本，这个作品在视频里毫无吸引力，这是最大的风险；
- PyOD 偏表格数据，时序需要自己滑窗处理；
- Anomalib 是视觉不是时序，**别混着讲**，容易让评委觉得你没想清楚。

**适合**：队里有工科/自动化背景，或能联系到有设备的实验室。

## 5. 组合建议

**如果你只能选一套，我会选方案 1。** 理由：

- 底座全是 MIT（除 Langfuse 需自查），许可证干净；
- "失败可回放可自愈"这个角度**几乎没人做**，天然差异化；
- 有 OSWorld 提供可复现评分，指标好量化；
- 演示画面天然好看（截图、回放、自愈过程）；
- 降级路径清晰，砍到最后还能交。

**如果你想要最稳的**：方案 3（安全评测平台），不需要私有数据、不依赖硬件、演示节奏好控制。

**如果队里有工科背景**：方案 7（设备预测性维护），有公开数据集、指标硬、工业故事好讲，而且"LLM 故障归因"这个增量在参赛作品里几乎没人做。

**如果你想冲一等奖**：方案 2 + 方案 1 的思路融合——做一个 **"可信智能体"**：Agent + 不确定性驱动的拒答 + 全轨迹审计。把"自主性"和"可信性"两个热点绑在一起，创新性拉满，但**风险也拉满，10/05 跑不通就必须砍**。

## 6. ⚠️ 关于维/哈语方向（重要更新）

我在前一份文档里把"多语种窗口服务台"列为首选。**补充一个必须知道的风险发现**：

调研显示，维吾尔语/哈萨克语的开源语音支持**整体偏弱**：

| 项目 | 可信度 | 说明 |
|---|---|---|
| [IS2AI/TurkicASR](https://github.com/IS2AI/TurkicASR) | 中高 | 哈萨克斯坦 ISSAI，一个模型覆盖 10 种突厥语含维语、哈语，有 Interspeech 论文与开源权重。但**社区资料极少，9 天内需自建推理管线** |
| facebookresearch/mms（MMS-1B） | 中 | 官方多语模型，模型卡含 Uyghur/Kazakh，但**低资源语种 WER 偏高，必须实测** |
| osman/whisper-small-ug、ixxan/ug-speech 等社区项目 | 低-中 | 个人微调、无权威评测，**只适合做 demo** |

**结论**：
1. **不要把维/哈语语音识别当作作品的核心卖点**，否则演示当场翻车的概率很高；
2. 正确用法是**文字输入为主 + 语音播报为辅**，或者**把维/哈语语音作为"差异化解题加分项"而不是核心功能**；
3. **如果一定要做语音，10/02 那天就要拿 TurkicASR 或 MMS 实测字错率**，达不到可用水平立刻退回纯文字方案；
4. 材料里**绝对不要宣称精度数字**，写了就要有评测支撑。
